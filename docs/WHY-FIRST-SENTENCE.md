# 为什么盯「第一句」

> 这篇只讲一件事：为什么一个语言策略插件，判据是「第一句」，而不是「全部用中文」。

## 一、现象：一句英文，整段英文

264 个含 reasoning 的会话里，`首句英文 → 整段英文主导 81.1%（60/74）`，`首句中文 → 整段英文主导 1.1%（2/190）`。

不是「英文任务会导致英文思考」这种模糊相关，而是几乎确定的条件关系。首句一旦落成英文，后面 20 段、40 段会一路英文到底——自回归把第一个 token 的选择放大成了整段的语言。

## 二、锚的位置决定成败

按 system prompt 里实际携带的锚分层：

| 锚 | 会话数 | 英文主导率 |
|---|---|---|
| 无任何锚 | 12 | 75.0% |
| 仅头部锚 | 73 | 39.7% |
| 头部 + 尾部锚 | 179 | 13.4% |

头锚把英文主导从 75% 压到 40%，尾锚再压到 13%。但 **13.4% 不是 0**，因为两者都在 system prompt 内部——而真正贴着采样点的位置，往往不是 system prompt 的结尾。

真实会话里，system prompt 有 43,523 字符，尾锚距离末尾仅 75 字符——听起来已经很近，可 system 之后还插着 15,621–16,704 字符的 user 文本（AgentTeams 派单模板 + system-reminder）。约束被稀释了。

## 三、三次尝试，两次败在「怎么测」

第一版用黑名单：禁止 `Let me`、`Let's`、`I'll`、`We need to` 开头。实测发现模型自创了 `The user wants…`、`The task: …`——**枚举永远不完备**。这是第一次失败，属于机制选错。

第二版改可判定判据（第一句必须含中文字符、不得以 ASCII 字母开头），并加 per-request 通道。实测 5.4%（3/56），仍未达标。但两次「失败」里，只有第一次是真的功能失败，后两次都是**测量失败**：

- 一次是样本时效：拿修复前的会话去证明修复后无效
- 一次是判定脚本的 marker 过滤：first-step 文本是「【首步】…」，而脚本按「【本步语言要求」过滤，把它整条跳过了

教训：每次「失败」先问一句——是功能没做到，还是我没测对。

## 四、真正的漏点在 step0，不在工具之后

把 mid 组的 3 条残留英文样本拿出来看，三句全是同一形态：

```
The user wants me to read three specific files and compare them.
Need read three files.
I should start by reading the three files.
```

都是「读文件之前的动作描述」，都发生在**第一次 assembly**。而当时实现的「工具结果之后」变体，要等 `tool/result` 之后才生效——结构上管不到首句。

所以加了 `first-step` 变体：step0 专用，给中文动作示范，点名禁止上述四类起手，并且整个 step0 期间不推进 step 计数，让该 step 的所有调用都命中它。

结果：mid 组 **0/80**，Wilson 双侧 [0, 4.6%]。

## 五、边界（比结论更重要）

- **提示层，不是硬开关**。它能提高中文 token 的概率，不能禁止英文采样。
- **0/80 只覆盖 mid 类任务**（读 2–3 个文件交叉对比）。long 类（工具链长、段数多）本轮未单独重测。
- **与 v1.0.0 的区间重叠**（[1.8%, 14.6%] vs [0, 4.6%]）。所以「达标」的依据是上界 ≤5%，而不是「显著优于上一版」——这两件事必须分开说。
- **强制的代价**：英文技术语料密度更高，代码/数学类任务英文 CoT 有时更准。用插件等于用「语言一致性」换「部分任务表现」，所以它提供三档 preset 与 `off` 开关。

## 六、如果继续往下压

mid 已到 0/80，再往下是 long 组。要判 long 是否也 <5%，需要按同样口径跑 n≥75 的分层 probe（约 110k token / 40 分钟）。这不是加一段提示词能解决的，得先看数据。
